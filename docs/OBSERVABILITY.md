## Metrics (Prometheus, `server/utils/metrics.js`)

| Metric | What it answers |
|---|---|
| `http_request_duration_seconds{method,route,status_code}` | Latency and traffic per route. The label is the route template (`/course/:id`), so ids never create new series |
| `learnify_cache_requests_total{namespace,result}` | Catalog cache hit ratio (`wait` = filled by a concurrent request: stampede protection working) |
| `learnify_outbox_events{status}`, `learnify_outbox_oldest_pending_age_seconds` | Is the relay keeping up? Lag here means events are not being published |
| `learnify_events_processed_total{consumer,outcome}`, `learnify_event_processing_duration_seconds` | Per-consumer throughput, failures, duplicates skipped, handling time |
| `rabbitmq_queue_messages{queue}` (RabbitMQ's own exporter) | Queue depth; anything in a `.dlq` needs a human |
| `learnify_search_requests_total{engine,kind}` | Whether search is on Elasticsearch or the MongoDB fallback |
| `learnify_circuit_breaker_open{breaker}` | Which dependency is failing fast right now |
| `learnify_orders_fulfilled_total{source}`, `learnify_webhook_deliveries_total{outcome}`, `learnify_socket_connections` | Business and realtime activity |
| default `process_*`, `nodejs_*` | Memory, CPU, event-loop lag |

Gauges such as outbox lag are computed when Prometheus scrapes, from the database itself, so they are correct
however many API instances run. `/metrics` is open in development. In production, set `METRICS_TOKEN` and give
it to Prometheus as a bearer token.

**Alerts** (`observability/alerts.yml`) are written as symptoms a user would notice: error rate above 5%, p95
above 1 s, outbox lag above 5 minutes, messages in a dead-letter queue, a circuit breaker open.

The dashboard JSON is generated by `observability/grafana/makeDashboard.js`, so panels are edited as code.

## Tracing (OpenTelemetry, `server/tracing.js`)

Enabled with `OTEL_EXPORTER_OTLP_ENDPOINT`. Auto-instrumentation covers HTTP, Express, MongoDB/Mongoose and
Redis. One trace follows a request across process boundaries:

```
learnify-api: POST /api/v1/reach/contact
  mongoose.OutboxEvent.save                       (event written in the request)
  learnify.events publish contact.submitted       (relay, later, in the same trace)
    email process contact.submitted               (consumer, possibly another process)
      mongoose.ProcessedEvent.findOne / save      (idempotency check)
```

Two things needed explicit work:

- **The outbox breaks the context.** The relay publishes seconds later, outside the request. The W3C
  `traceparent` is stored on the outbox row, and the relay publishes inside that context
  (`utils/traceContext.js`).
- **The amqplib instrumentation does not support amqplib 2.x.** Producer and consumer spans are created in
  `config/rabbit.js`, and the context travels in the message headers. Retries copy headers, so a retried
  message stays in the same trace.

Database and Redis spans are recorded only inside a request or message trace (`requireParentSpan`).
Otherwise the relay's once-a-second poll would produce a trace every second.

## API documentation (`server/openapi/generate.js`)

The OpenAPI 3.1 document is generated from the running Express router, not written by hand, so it cannot
drift. The generator walks every mounted router and reads:

- the methods and paths,
- the request schema from the route's zod validator (`z.toJSONSchema`),
- metadata the middleware carries:
  - `auth` adds bearer security and a 401 response;
  - `requirePermission` or a role check adds the permission or role and a 403 response;
  - `idempotent()` adds the `Idempotency-Key` header and 409/422 responses;
  - the internal router adds the `X-Internal-Token` scheme.

Served at `/api/docs` (Swagger UI) and `/api/openapi.json`.

## Instructor webhooks (`server/utils/webhooks.js`)

Instructors subscribe a URL to `enrollment.created`, `review.created`, `course.published` and
`course.rejected` (Dashboard → Webhooks).

```
domain event (outbox) ─▶ "webhook-fanout" consumer ─▶ one delivery row + one message per subscription
                                                     (one transaction; unique per source event)
                         "webhook-delivery" consumer ─▶ signed POST, 5 s timeout
                                                      failure → retry 10 s, 1 min, 5 min, 30 min → failed
```

- **Signature:** `Learnify-Signature: t=<unix>,v1=<HMAC-SHA256(secret, "t.body")>`. Receivers compare with
  a constant-time check and reject old timestamps (replay protection). `Learnify-Delivery` is stable across
  retries for receiver-side de-duplication. The page shows a verification snippet.
- **Secrets** are shown once, stored AES-256-GCM encrypted (they must be recoverable to sign), and can be
  rotated.
- **SSRF protection:** https only in production, no credentials in URLs, no redirects followed. Hosts that
  resolve to loopback, private, link-local (cloud metadata) or other internal ranges are refused, both when
  saved and before every delivery (DNS rebinding).
- **Isolation:** each delivery is its own message, so one slow endpoint never delays another instructor's.
  After 15 consecutive failures a webhook is paused and the instructor is notified.
- **Public contract:** webhook event names and payloads are separate from internal event names, so the
  internals can change without breaking integrations.
